# Режимы пула

pg_doorman поддерживает два режима пула: `transaction` и `session`. Режим задаётся для пула, при необходимости переопределяется для конкретного пользователя.

Режима `statement` нет. В statement-пулинге серверное соединение ротируется после каждого оператора — это вынуждает клиентов отказаться от мульти-statement транзакций и полностью ломает протокол prepared statements. Все оптимизации pg_doorman (кеш prepared statements, прямая передача, строгий FIFO-планировщик) рассчитаны на транзакционный режим. PgBouncer оставляет `statement` для обратной совместимости; Odyssey его не реализует.

## Транзакционный режим (рекомендуется)

```yaml
pools:
  mydb:
    pool_mode: "transaction"
```

Backend-соединение удерживается в течение транзакции и возвращается в пул при `COMMIT`, `ROLLBACK` или неявном завершении.

Именно этот режим даёт ту самую эффективность соединений, ради которой существует pg_doorman: `pool_size` равный 40 обслуживает тысячи клиентов, пока транзакции остаются короткими.

Что работает в транзакционном режиме (там, где большинство пулеров проваливаются):

- Prepared statements. pg_doorman кеширует их в рамках пула, переименовывает имена statement между backend-соединениями и прозрачно повторно готовит запрос. Драйверы, привязанные к `unnamed`-statement (Go pgx, .NET Npgsql, Python asyncpg), работают без настройки.
- SQL-команда `PREPARE`. Клиент удерживает backend, пока созданные так statements существуют (`DEALLOCATE`, `DEALLOCATE ALL`, `DISCARD ALL`). Протокольный `Close` такого statement backend не освобождает, а при `prepared_statements = false` клиент, отправлявший и именованный `Parse`, держит его до `DEALLOCATE ALL`, `DISCARD ALL` или отключения: pg_doorman не может определить, statement какого вида удалил `DEALLOCATE`.
- Pipelined-батчи и асинхронный поток `Flush`.
- Cancel-запросы поверх TLS.
- `LISTEN` / `NOTIFY` — но только внутри транзакции. `LISTEN` после `COMMIT` отпускает backend, и любые уведомления, доставленные ему после, попадут к тому клиенту, который следующим заберёт это соединение, а не к исходному `LISTEN`-еру. PgBouncer ведёт себя так же; если вам нужен `LISTEN` через несколько транзакций, для этого клиента используйте сессионный режим.

Что в транзакционном режиме **не работает**:

- `SET` и `RESET` вне транзакции. Используйте сессионный режим для клиентов, опирающихся на изменение GUC уровня сессии (`SET TIME ZONE`, `SET search_path` один раз на соединение).
- advisory-блокировки, удерживаемые между транзакциями. Используйте сессионный режим.
- курсоры, удерживаемые вне транзакций (`WITH HOLD`). Используйте сессионный режим.
- `SET LOCAL` работает как ожидается — он ограничен транзакцией.

### Клиент отключился во время запроса

Если клиент отключился, пока PostgreSQL ещё выполняет его запрос, pg_doorman держит backend за ним до конца запроса. Запрос, закончившийся за секунду, дочитывается, и backend после обычной очистки возвращается в пул. Более долгий запрос отменяется через CancelRequest, и backend закрывается, как только PostgreSQL ответит, или через 10 секунд после отмены. Всё это время слот пула занят, поэтому backend, который его займёт, никогда не работает рядом с брошенным запросом.

Так же и тогда, когда клиент отключился, пока DataRow, CopyData или результат вызова функции больше `message_size_to_be_stream` передавался ему по частям: pg_doorman всё равно дочитывает это сообщение из PostgreSQL, и backend остаётся пригодным.

Не покрыт один случай: если PostgreSQL уже отправил часть ответа, например NOTICE, pg_doorman не следит за клиентом, пока не дочитает этот ответ до конца или пока полученные строки не заполнят буфер до `response_flush_threshold`. Только после этого он может заметить отключение. Следующие NOTICE копятся в буфере вместе с остальным ответом и чтение не завершают. До тех пор backend остаётся за ушедшим клиентом, и запрос не отменяется.

## Сессионный режим

```yaml
pools:
  legacy_app:
    pool_mode: "session"
```

Backend-соединение удерживается в течение клиентской сессии. В пул возвращается только при отключении клиента.

Используйте, когда:

- Приложение использует состояние уровня сессии (`SET search_path`, `SET TIME ZONE`).
- Приложение использует курсоры WITH HOLD.
- Приложение использует advisory-блокировки между транзакциями.
- Вы переезжаете с немодифицированного PgBouncer-развёртывания, работавшего в сессионном режиме, и хотите подмену один-в-один.

В сессионном режиме `pool_size` фактически равен максимальному числу одновременных клиентов. Размер пула подбирается так, чтобы соответствовать `max_connections` PostgreSQL минус резервы.

## Переопределение для конкретного пользователя

Режим пула можно переопределить для конкретного пользователя:

```yaml
pools:
  mydb:
    pool_mode: "transaction"
    users:
      - username: "app"
        password: "md5..."
        pool_size: 40
      - username: "admin_tools"
        password: "md5..."
        pool_size: 4
        pool_mode: "session"
```

Полезно, когда одному пользователю (инструменты эксплуатации, миграции) нужна семантика сессии, а основное приложение остаётся в транзакционном режиме.

## Очистка при возврате в пул

Очистка в транзакционном режиме **отслеживает мутации**: pg_doorman следит за каждой транзакцией на предмет `SET`, `PREPARE` и `DECLARE CURSOR`, и только когда backend уходит в пул с одним из этих флагов, отправляет соответственно `RESET ALL`, `DEALLOCATE ALL` или `CLOSE ALL`.

Состояние сессии, о котором PostgreSQL не сообщает в протоколе, например advisory-блокировки и переменные `pg_variables`, так отследить нельзя. Его сбрасывает `release_query` пула при каждом возврате backend, по умолчанию запросом `SELECT pg_catalog.pg_advisory_unlock_all(), public.pgv_free();`. Запрос по умолчанию PgDoorman отправляет в PostgreSQL при возврате backend в пул, после нужных сессии `RESET ALL`, `DEALLOCATE ALL` или `CLOSE ALL`, и результата не ждёт: PostgreSQL выполняет его сразу, блокировки снимаются тут же, а результат PgDoorman читает перед следующим обменом с этим backend. Запрос выполняется внутри `BEGIN` и `COMMIT` операторами, подготовленными один раз на backend под именами `DOORMAN_release_begin`, `DOORMAN_release` и `DOORMAN_release_commit`; их видно в `pg_prepared_statements`, а после `DEALLOCATE ALL` или `DISCARD ALL` PgDoorman готовит их заново. Если запрос завершился ошибкой, например в него попал запрос отмены, PostgreSQL пропускает всё, что прислал следующий клиент, до его `Sync`. Ничего из этого не выполняется в сессии, которую запрос не очистил: в режиме transaction клиент получает ошибку с SQLSTATE `08006` о том, что запрос не выполнен, и остаётся подключённым, в режиме session соединение закрывается с этой ошибкой, а backend закрывается. Если ошибка уже пришла к моменту, когда backend берут из пула, backend просто заменяется. Свой `release_query` и очистка backend, возвращённого внутри транзакции, сохраняют отдельное обращение: backend остаётся занятым, пока оно не завершится. Пулам, приложения которых не держат между транзакциями ни advisory-блокировок уровня сессии, ни переменных `pg_variables`, можно выставить `release_query = ""`; advisory-блокировки уровня транзакции (`pg_advisory_xact_lock`) PostgreSQL снимает сам при фиксации.

Что сбрасывается, когда сработал флаг:

- Флаг `SET` → `RESET ALL` сбрасывает session-level GUCs.
- Флаг `PREPARE` → `DEALLOCATE ALL` удаляет PostgreSQL-side prepared statements, которые драйвер именовал явно. Собственный кеш prepared statements pg_doorman сохраняется после сброса: он индексируется текстом запроса, а не backend-именем.
- Флаг `DECLARE CURSOR` → `CLOSE ALL` закрывает курсоры.

`DEALLOCATE ALL` со стороны клиента очищает prepared-statement-кеш именно этого клиента (следующий `Parse` зарегистрируется заново); `DISCARD ALL` его сохраняет, а `Bind` на бэкенде без нужного statement сначала готовит его там. Pool-level shared cache не затрагивается; у других клиентов их записи сохраняются. Клиенту без бэкенда (вне транзакции и без statements, созданных SQL `PREPARE`) на `DEALLOCATE ALL` отвечает сам pg_doorman: statements на бэкендах общие для всех клиентов.

Полностью отключить очистку (ради производительности в жёстко контролируемых развёртываниях):

```yaml
pools:
  mydb:
    pool_mode: "transaction"
    cleanup_server_connections: false
```

Делайте так только если уверены, что приложение никогда не оставляет состояние сессии. Очистка по мутациям ничего не стоит на транзакциях без мутаций, поэтому отключение редко стоит риска. На `release_query` оно не влияет: он настраивается отдельно.
