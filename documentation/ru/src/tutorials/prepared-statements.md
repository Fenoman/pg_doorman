# Prepared statements в transaction pooling

PgDoorman сохраняет возможность использовать prepared statements клиента,
когда разные транзакции обслуживают разные бэкенды PostgreSQL. Именованные и
анонимные statements отображаются в служебные имена `DOORMAN_<N>`.

## Один statement на бэкенде для одной формы запроса

`Parse` с одинаковыми SQL, OID параметров и стартовыми настройками планировщика
используют одну запись пула и одно служебное имя. Если выбранный бэкенд уже
держит это имя, PgDoorman отвечает на `Parse` синтетическим `ParseComplete` и не
передаёт его в PostgreSQL; иначе `Parse` уходит на бэкенд под этим именем.
Последующий `Bind` или `Describe` на бэкенде без этого имени сначала готовит
statement там, сохраняя порядок ответов клиентского протокола. Поэтому бэкенд
держит один statement на каждую обслуженную форму запроса, а не на каждый вызов
или клиента. Запись пула, вытесненная и добавленная снова, получает новое
служебное имя; прежнее остаётся на бэкендах, пока его не уберёт их LRU или
очистка.

```text
Клиент A: Parse("old", SQL)   -> PostgreSQL: Parse("DOORMAN_42", SQL)
Клиент B: Parse("new", SQL)   -> бэкенд держит DOORMAN_42: синтетический ParseComplete
Клиент A: Bind("old")         -> PostgreSQL: Bind("DOORMAN_42")
Клиент B: Bind("new")         -> PostgreSQL: Bind("DOORMAN_42")
```

Пропуск повторного `Parse` избавляет PostgreSQL от повторного разбора уже
подготовленного запроса. Выбор PostgreSQL между custom- и generic-планом для
statement на бэкенде общий для всех клиентов, которые используют его там,
поэтому он может отражать смешанные значения их параметров. Пул
разделяет между клиентами неизменяемые `Arc<Parse>`, SQL и массивы OID
параметров.

Клиент, отправивший `Flush`, получает новое служебное имя на каждый следующий
`Parse`. Его копии ограничены только `server_prepared_statements_cache_size` на
каждом бэкенде. Миграция при бинарном обновлении восстанавливает то же
именование.

## Изменение схемы

Пропущенный `Parse` не разбирается заново. После DDL, меняющего форму
результата, например `ALTER TABLE ... ADD COLUMN` под `SELECT *` или изменения
типа результата функции, первый `Bind` statement, подготовленного до DDL, на
каждом бэкенде завершается ошибкой `0A000` (`cached plan must not change result
type`). При прямом подключении свежий `Parse` разобрался бы по новой схеме.

Любая ошибка PostgreSQL назначает `DEALLOCATE ALL` на момент возврата бэкенда в
пул; при `cleanup_server_connections = false` бэкенд вместо этого закрывается.
Следующий `Parse` на этом бэкенде готовится уже по новой схеме, поэтому каждый
бэкенд сообщает об ошибке один раз на каждое такое изменение схемы. Пулер не
повторяет исполнение SQL для сокрытия этой ошибки.

Очистка ждёт возврата бэкенда в пул. До этого `Parse` такого запроса по-прежнему
обслуживается устаревшим statement, и его следующий `Bind` или `Describe` снова
завершается ошибкой: в той же транзакции после отката к точке сохранения (без
неё прерванная транзакция отвечает `25P02`) и в каждой следующей транзакции
сессии, выполнившей SQL-команду `PREPARE`, потому что такая сессия удерживает
свой бэкенд. `RECONNECT <database>` в админ-консоли сразу закрывает простаивающие
бэкенды, а занятые — при их возврате в пул.

Если `Bind` старого statement приходит на бэкенд, который его уже не держит,
statement готовится там заново, поэтому форма результата следует текущей схеме
этого бэкенда. Transaction pooling не может сохранить описание, которое существовало
только в очищенном или закрытом бэкенде.

Новое служебное имя на каждый `Parse` избавляло от `0A000`, но оставляло
прежнюю копию на бэкенде, где она была создана. В transaction pooling это
заполняло каждый бэкенд дубликатами планов до
`server_prepared_statements_cache_size`.

## Слои кеша и ограничения

| Слой | Содержимое | Ограничение |
| --- | --- | --- |
| Пул | Общие метаданные Parse по SQL, OID параметров и стартовым настройкам планировщика | `prepared_statements_cache_size` |
| Клиент, именованные | Имя клиента, logical statement и имя на бэкенде | 2048 записей на клиента |
| Клиент, анонимные | Записи по хешу и текущий доступный unnamed statement | `client_anonymous_prepared_cache_size`; ноль выбирает неограниченную map |
| Бэкенд | Служебные имена, подготовленные в этом PostgreSQL | `server_prepared_statements_cache_size` |

Без явного значения клиентский и серверный кеш наследуют размер prepared-кеша
пула. Вытеснение из серверного кеша отправляет Close; следующий Bind может
подготовить statement заново. Вытеснение пуловых метаданных не удаляет записи,
на которые ещё ссылаются клиенты.

Замена клиентской записи с другим именем на бэкенде планирует закрытие
прежнего имени на текущем бэкенде после успешного нового Parse. Так бывает,
когда именованный statement заново подготовлен с другим запросом, при каждом
повторном Parse клиента, отправлявшего `Flush`, и после вытеснения и повторного
добавления записи пула. В остальных случаях повторный Parse того же запроса
сохраняет имя и ничего не закрывает. Ошибка именованного Parse восстанавливает
прежнюю клиентскую запись; после ошибки безымянного Parse безымянного statement
нет, как и в PostgreSQL.
Вытеснение из Anonymous LRU удаляет локальную запись; серверный LRU и ротация
бэкендов ограничивают время жизни физических statements на других соединениях.
Вытеснение из-за лимита Named учитывается отдельно от обычной замены записи.

Query interner устраняет дубли SQL и имеет отдельные настройки GC/TTL. Его
память отличается от памяти планов PostgreSQL. Настройки
`query_interner_gc_interval_seconds` и `query_interner_anon_idle_ttl_seconds`
описаны в справочнике конфигурации.

## Конфигурация

```toml
[general]
prepared_statements = true
prepared_statements_cache_size = 8192
server_prepared_statements_cache_size = 1024
client_anonymous_prepared_cache_size = 256
```

Это пример размеров, а не универсальная рекомендация. Размер серверного кеша
выбирают по измеренной памяти планов и частоте повторной подготовки, клиентского
— по рабочему набору сессии. `max_memory_usage` ограничивает буферы обработки
сообщений и не является лимитом памяти prepared-кеша.

При `prepared_statements = false` сообщения используют исходные имена PostgreSQL.
Отключение меняет совместимость именованных statements с transaction pooling и
не заменяет измерение выбранного режима.

## Наблюдаемость

`SHOW POOLS_MEMORY` показывает состояние пуловых и клиентских кешей.
`SHOW PREPARED_STATEMENTS` и prepared-разделы веб-интерфейса описывают общие
пуловые записи: их имена совпадают с физическими именами на бэкендах, кроме
клиентов, отправлявших `Flush`.

Счётчики hit/miss пуловой prepared-записи фиксируют путь, выбранный для каждого
`Parse`: hit означает, что PgDoorman ответил без передачи в PostgreSQL, потому
что бэкенд держит statement или его готовит более ранний `Parse` того же
пакета; miss — что `Parse` был передан. Попадания в кеш бэкенда
учитывают также последующие Bind/Describe.

`pg_prepared_statements` показывает реальные имена и планы на том бэкенде,
который исполняет проверку. Счётчики вытеснений Anonymous и Named отражают
переполнение соответствующих клиентских кешей. Повторная замена той же
анонимной записи не увеличивает счётчик вытеснений Named.

После выкладки новой версии проверьте `SHOW SERVERS` под нагрузкой, близкой к
рабочей. `prepare_cache_size` каждого бэкенда должен установиться около числа
различных запросов приложения. Значение, которое растёт к
`server_prepared_statements_cache_size`, означает, что бэкенды копят
дубликаты планов за счёт памяти PostgreSQL. Для драйверов, которые делают Parse
на каждый вызов, тот же дефект снижает долю попаданий серверного кеша; за ней
следит алерт **`PgDoormanPreparedHitRatioLow`** из
`monitoring/prometheus-rules/prepared-statements.yaml`.
