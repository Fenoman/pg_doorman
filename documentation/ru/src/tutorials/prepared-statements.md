# Prepared statements в transaction pooling

PgDoorman сохраняет возможность использовать prepared statements клиента,
когда разные транзакции обслуживают разные бэкенды PostgreSQL. Именованные и
анонимные statements отображаются в служебные имена `DOORMAN_<N>`.

## Новый Parse создаёт новый statement на бэкенде

Каждый клиентский `Parse`, обрабатываемый кешем prepared statements, передаётся
PostgreSQL с новым служебным именем. PostgreSQL проверяет запрос относительно
схемы, видимой этому подключению, и возвращает `ParseComplete`. Совпадение SQL,
OID параметров и стартовых настроек планировщика позволяет разделять метаданные
в памяти пулера, но не означает совпадение актуального описания результата.

Это различие существенно после `ALTER TABLE`, пересоздания временной таблицы,
изменения результата функции или DDL через другое подключение. Новый именованный
или анонимный `Parse` получает новую структуру результата, как при прямом
подключении к PostgreSQL. Подготовка после отката DDL использует восстановленную
схему.

Ранее подготовленный statement сохраняет прежнее имя на бэкенде. Его `Bind`
после несовместимого изменения результата может вернуть ошибку PostgreSQL
`0A000` (`cached plan must not change result type`). Новый Parse не подменяет
старый statement. Пулер не повторяет исполнение SQL для сокрытия этой ошибки.

Если старый Bind попадает на другой бэкенд или его statement вытеснен из
серверного кеша, нужен новый внутренний Parse. Описание результата тогда
строится по текущей схеме выбранного бэкенда. Transaction pooling не может
сохранить описание, которое существовало только в закрытом бэкенде PostgreSQL
или в вытесненном statement.

## Повторное использование и производительность

Повторные `Bind`/`Execute` без нового Parse используют прежний logical statement.
Если выбранный бэкенд уже знает его служебное имя, PostgreSQL может использовать
подготовленный план. Иначе пулер сначала подготавливает statement на этом
бэкенде, сохраняя порядок ответов клиентского протокола.

Драйвер, отправляющий новый анонимный Parse на каждый вызов, оплачивает подготовку
в PostgreSQL на каждом вызове. Пулер больше не синтезирует ParseComplete для
совместного использования физического плана разными новыми Parse или клиентами.
Для повторяющихся запросов можно использовать API постоянных именованных
statements в драйвере, если это подходит приложению. Эффект нужно измерять на
реальном драйвере и нагрузке: увеличение кеша не возвращает пропуск Parse.

Общие неизменяемые `Arc<Parse>`, SQL и массивы OID параметров по-прежнему
разделяются между клиентами. Каждый logical statement хранит отдельное имя
бэкенда и клиентский учёт. Миграция восстанавливает отдельные имена с общими
метаданными.

```text
Клиент A: Parse("old", SQL)   -> PostgreSQL: Parse("DOORMAN_42", SQL)
Клиент B: Parse("new", SQL)   -> PostgreSQL: Parse("DOORMAN_43", SQL)
Клиент A: Bind("old")         -> PostgreSQL: Bind("DOORMAN_42")
Клиент B: Bind("new")         -> PostgreSQL: Bind("DOORMAN_43")
```

## Слои кеша и ограничения

| Слой | Содержимое | Ограничение |
| --- | --- | --- |
| Пул | Общие метаданные Parse по SQL, OID параметров и стартовым настройкам планировщика | `prepared_statements_cache_size` |
| Клиент, именованные | Имя клиента, logical statement и имя на бэкенде | 2048 записей на клиента |
| Клиент, анонимные | Записи по хешу и текущий доступный unnamed statement | `client_anonymous_prepared_cache_size`; ноль выбирает неограниченную map |
| Бэкенд | Служебные имена, подготовленные в этом PostgreSQL | `server_prepared_statements_cache_size` |

Без явного значения клиентский и серверный кеш наследуют размер prepared-кеша
пула. Вытеснение из серверного кеша отправляет Close; следующий Bind может
подготовить statement заново. Вытеснение пуловых метаданных не удаляет записи,
на которые ещё ссылаются клиенты.

Замена клиентской записи планирует закрытие её прежнего имени после успешного
нового Parse. Ошибка Parse восстанавливает прежнее пространство имён клиента.
Вытеснение из Anonymous LRU удаляет локальную запись; серверный LRU и ротация
бэкендов ограничивают время жизни физических statements на других соединениях.
Вытеснение из-за лимита Named учитывается отдельно от обычной замены записи.

Query interner устраняет дубли SQL и имеет отдельные настройки GC/TTL. Его
память отличается от памяти планов PostgreSQL. Настройки
`query_interner_gc_interval_seconds` и `query_interner_anon_idle_ttl_seconds`
описаны в справочнике конфигурации.

## Конфигурация

```toml
[general]
prepared_statements = true
prepared_statements_cache_size = 8192
server_prepared_statements_cache_size = 1024
client_anonymous_prepared_cache_size = 256
```

Это пример размеров, а не универсальная рекомендация. Размер серверного кеша
выбирают по измеренной памяти планов и частоте повторной подготовки, клиентского
— по рабочему набору сессии. `max_memory_usage` ограничивает буферы обработки
сообщений и не является лимитом памяти prepared-кеша.

При `prepared_statements = false` сообщения используют исходные имена PostgreSQL.
Отключение меняет совместимость именованных statements с transaction pooling и
не заменяет измерение выбранного режима.

## Наблюдаемость

`SHOW POOLS_MEMORY` показывает состояние пуловых и клиентских кешей.
`SHOW PREPARED_STATEMENTS` и prepared-разделы веб-интерфейса описывают общие
пуловые записи: их канонические имена могут отличаться от физических имён
на конкретном бэкенде.

Счётчики hit/miss пуловой prepared-записи относятся к повторному использованию
физического плана в момент Parse. Новые Parse теперь дают miss. Попадания в кеш
бэкенда по-прежнему отражают повторные Bind/Describe. Нулевая доля попаданий
на Parse не означает отсутствия переиспользования планов постоянными
именованными statements.

`pg_prepared_statements` показывает реальные имена и планы на том бэкенде,
который исполняет проверку. Счётчики вытеснений Anonymous и Named отражают
переполнение соответствующих клиентских кешей. Повторная замена той же
анонимной записи не увеличивает счётчик вытеснений Named.
